## Validation

Offline checks (not VM compatibility evidence):

```sh
go test -mod=vendor ./internal/vm -run 'TestCentOS|TestAllProfileYAML' -count=1
go test -mod=vendor -race -count=1 ./...
go vet -mod=vendor ./...
bash scripts/action-prebuilt-checksums_test.sh
bash scripts/action-artifact-ref-detection_test.sh
git diff --check
```

The CentOS guard checks exact URLs, rejects obsolete names, restricts the
maintenance catalog to the baseline profiles, and checks inherited base
fields after removing the three kernel-sweep overrides. This matches the
base-copy generation in `cmd/bpfcompat/kernel_sweep.go`.

Live evidence must be retained outside the source tree in a dedicated
temporary directory. Copy profile definitions there unchanged and run from
that directory so relative `vm/cache` paths cannot use existing images.
Use the exact candidate CLI, an independently hashed static validator, and
positive load/required-attach and classified negative fixtures. Keep image
SHA-256, observed `uname`, reports, serial logs, exit codes and build identity.
Verify hashes independently: this baseline caches image hash sidecars and
does not emit main's `.validator.sha256` report field.

Download/boot/SSH failures are `INFRA_ERROR`, not `INCOMPATIBLE`. Missing
reports or wrong kernel identity are incomplete evidence, not success.
Explicitly record untested sweep installation and published-Action paths.
Local binaries are not signed/attested release assets. A build with Go older
than the release workflow's 1.25.14 does not meet release-toolchain readiness.

## Release workflow compatibility: blocked

The baseline binary workflow produces SHA256SUMS, cosign v2.6.3 signatures,
binary provenance and an SBOM attestation, but attaches assets through
`softprops/action-gh-release` without draft-only staging or separate
promotion. The separate tag-triggered container workflow can publish
production aliases independently. Do not tag this branch in its current state.

Compare against the release controls at upstream main
`94686618fa5315850a6473694cd7714cbdf6a613`. Minimum reviewed follow-up work:

1. Preserve explicit downloaded-asset checksum verification, signed checksum
   and SBOM artifacts, exact-workflow signature/attestation verification, and
   immutable tags. Do not weaken runner verification or allow source fallback
   to masquerade as prebuilt consumption.
2. Add fail-closed live repository/environment checks and already-public
   release mutation refusal. Keep the production wait and operator confirmation.
3. Separate candidate build/test/sign/draft staging from explicit promotion;
   remove independent production alias writers only through reviewed changes.
4. Bind evidence to full commit, tag/channel, workflow run and attempt, binary
   hashes, image digest and actual VM reports. Adapt the exact-artifact gate
   for the old report: main's validator identity assertion is unsupported here.
   Hash staged validator bytes in an external harness without changing runtime.
5. Resolve metadata/canary bootstrap sequencing before adding current pin
   guards. Keep stable consumer pins on the existing published stable release
   until a new release exists; never use tag-object SHAs or mutable refs.
6. Preserve current readiness requirements: four scheduled 6-8-day-spaced
   campaigns, zero infrastructure errors, 12-minute target p95, five Falco
   profiles, exact-candidate manual/T+24h/T+72h canaries, rollback/incident
   evidence and operator confirmation. Retarget old RC-specific canaries.

No policy exception is approved. Do not copy the main pipeline wholesale:
its scripts, metadata, pinned Ubuntu fixture and report expectations differ.
Pipeline adaptation needs its own focused review and regression tests before
any tag. Neither consumer repositories nor live protection settings may be
changed during this preparation.

Decision: source preparation may proceed; release candidate tag creation is
NO-GO until release controls and exact-candidate readiness evidence are complete.
