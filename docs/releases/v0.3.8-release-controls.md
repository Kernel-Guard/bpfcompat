# v0.3.8 maintenance release controls

This branch remains based on v0.3.7 (`179ff612ed2b5d1afb16dd9c282752028d47c415`).
It must not merge main. Runtime, CLI inputs, Action inputs/outputs, v0.1 reports,
Go dependencies and validator source are unchanged. Installation trust is
intentionally stricter: prebuilt Action downloads require a modern `gh` with
attestation support; the standalone installer requires cosign. Neither may
fall back to checksum-only installation. The v0.3.7 scoped checksum fix remains.

## Deterministic preparation sequence

1. Commit and review clean maintenance source. Published pin guards continue to
   resolve the actual v0.3.7 tag; no placeholder SHA or temporary guard bypass.
2. Build twice using exact Go 1.25.14, full HEAD and commit timestamp, vendored
   modules, fixed flags and locked native package versions. Record tool inputs.
3. Validate these exact binaries using `scripts/maintenance-vm-gate.sh` in a new
   absolute directory. Require positive load/attach, guest-validator identity,
   expected negative exit 2, three non-infrastructure targets and exact kernel 725.
4. Obtain explicit authorization before any tag/push. A future tag must equal
   `v` + release.yaml's target and point to the reviewed candidate HEAD. Existing
   immutable-tag rules prohibit updating/deleting v* tags without bypass actors.
5. Tag workflow verifies protection settings, quality/coverage/vulnerability
   gates, native ARM64 CLI, VM results, signatures and attestations; packages
   verified binary bytes into a candidate-only container. Only a draft is staged.
6. Separately authorized promotion dispatch on that exact tag requires full SHA,
   successful candidate run/attempt, digest, exact confirmation and operator.
   Protected production environment enforces the existing 15-minute wait,
   no-admin-bypass policy. Reverify run/draft identity, source-bound provenance,
   exact-tag signatures, container identity and (for stable) raw readiness input.
7. Only after public publication may a separate commit introduce a candidate
   canary's **actual** published SHA. Only after public stable v0.3.8 may published
   stable metadata/pins advance. Updating those lifecycle guards is separately
   reviewable, not a self-referencing candidate commit or policy exception.
8. Downstream updates wait for a suitable public release. Replace both version
   comments and immutable `uses:` SHA together; preserve OCI/command inputs,
   existing v0.1 report consumers and error handling. Never pin to main.

## Fail-closed boundaries and outstanding evidence

Local tests use offline mocks only for services/signatures they cannot create.
They do not prove OIDC issuance, remote signing, native ARM64 execution, container
publication or end-to-end workflow execution. No workflow was dispatched here.

The inherited `make production-tech-check` is retained as a mandatory gate. Its
stability subgate requires three ready historical beta-tech reports. A fresh
runner does not have that history; this must be supplied through a reviewed,
authenticated evidence acquisition path before the pipeline can proceed.
Do not generate three repeated local timestamps to counterfeit stability.

Stable readiness additionally requires four weekly scheduled campaigns, Falco
required-profile evidence, candidate provenance, manual/+24h/+72h canaries,
rollback and incident drills and operator evidence. These are not present in
this maintenance checkout. Adding external metadata generation/retention to old
workflows, if needed, is release-evidence work, not a report-schema migration.
No gate has been disabled to compensate for missing records.

The observed main scheduled campaign workflow emits metadata but does not
attest it; the observed Falco upstream workflow likewise uploads reports but
does not attest them. These observations cannot satisfy the strengthened
readiness provenance guard. Authentic collection/attestation must be designed
and reviewed separately; downstream changes are not authorized in this phase.
Do not replace authenticated observations with manually asserted hashes or
pass markers. This is an explicit stable-publication blocker, not a runtime
schema dependency and not permission to waive provenance.

Native packages are version-locked and builds are compared locally. Availability
of these exact packages on a fresh hosted runner and cross-runner byte-for-byte
reproduction remain separate validation requirements. Do not replace missing
versions with unpinned apt packages. SBOM/signature/attestation issuance for a new
candidate requires a later authorized GitHub run; local unsigned binaries are
not release assets. A draft is not usable by public SHA-pinned downstream Actions.
SBOM generation is pinned to Syft v1.54.1 and scans the built asset directory,
not a different container rebuild or the entire source/vendor tree.

Phase 4 logs, package signatures/hashes and actual VM reports are maintained in
an isolated temporary evidence directory, not the committed tree. The final
handoff identifies the tested HEAD and distinguishes PASS, FAIL, INFRA_ERROR,
NOT VERIFIED and BLOCKED. No production readiness approval is implied here.
