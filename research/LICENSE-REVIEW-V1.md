## BPFCompat-owned inputs

The controlled probes, manifests, BPFCompat v0.3.7 CLI, static validator,

## VM and vendor images

The study records exact image identities and observed environments. VM/base
images are not part of the default DOI redistribution set. The archive should
retain identities, provenance, requested kernel family, observed kernel release,
and acquisition/rebuild instructions instead.

## Required archival manifest

Before a DOI deposit, generate a machine-readable archive manifest with one row
per file containing at least:

- relative path;
- SHA-256;
- provenance class;
- owner/upstream project;
- source revision;
- redistribution status: `include`, `exclude-rebuildable`, or
  `include-with-notice`;
- associated license/notice paths.

Status semantics are fail-closed:

- plain `include` is valid only for `bpfcompat-owned` provenance;
- every third-party-derived file must be either `include-with-notice` or
  `exclude-rebuildable`;
- a third-party-derived row marked plain `include` is invalid;
- every `include-with-notice` row must name the applicable retained
  license/notice path(s), and every named path must exist in the archive;
- `exclude-rebuildable` rows retain identity/provenance/build metadata but the
  excluded binary/object itself must not be present in the DOI payload.

The archive generator/validator must enforce these rules and fail closed on any
violation.

## Implemented archive enforcement

The v1 archive policy is enforced by `scripts/research/archive-v1.py` and the
`research-archive-v1` CI workflow. The builder classifies every member of the
verified materialization artifact, fails on any unclassified member, rejects
plain `include` for third-party provenance, requires retained notice paths,
and verifies that `exclude-rebuildable` loader binaries are absent from the DOI
payload. Negative regressions exercise both the third-party-status rule and
excluded-loader injection rule.
